# 0400 D CRS check bound into payment (business payee)
New contract `contracts/CrsCheck.schema.json`: `{seller_id, verified, reason_codes[], product: fraud_finder|tu_identity, persona_id?, checked_at, request_id?, origin: SANDBOX|CACHED|NOT_CONFIGURED}`. A band only: `additionalProperties` is false, `reason_codes` are short codes (letters, digits, underscore, either case: the adapter sends `CRS_IDENTITY_VERIFIED` even when verified), so no raw report field (score, SSN, address) can ride along. `pay/crs_gate.py` adds `payee_ok(check, *, business, now, seller_id=None)`, `bound_ok(mandate, check, *, business, seller_id, now=None)` (seller_id is required with no default: a business payee with None or a different seller than the check's is refused as crs_seller_mismatch) and `check_id(check)`. A business payee is refused with no check, a blocked check, a NOT_CONFIGURED check, a malformed check, a check dated in the future, or one older than 24 hours; a SIM seller with no check passes with "identity not checked: SIM seller".
`contracts/Mandate.schema.json` gains an optional `crs_check_id`; it enters the mandate hash only when present, so every existing mandate hashes exactly as before (pinned in `pay/tests/test_crs_gate.py`).
Note for Lane A (Abhinav, #15): the CRS adapter should emit this shape (one `CrsCheck` per seller check, `reason_codes` mapped from the Fraud Finder and TU results, `origin: NOT_CONFIGURED` when there are no credentials). Lane D adds no second CRS login client: failed logins lock the shared sandbox account. `.env.example` takes main's CRS block as it stands: `CRS_USERNAME`, `CRS_PASSWORD`, `CRS_BASE_URL`, `CRS_API_KEY` (an optional preissued bearer token that skips login; agents/crs.py reads it) and `CRS_TEST_IDENTITIES_PATH`.
